Реализация ReadWriteLock с **writer-preference** и **без reentrancy** (один поток либо читает, либо пишет)

## Схема writer-preference (без reentrancy)

### 1) Что нужно поддерживать в состоянии
Внутренние поля (в терминах “переменных”, не кода):
- `activeReaders` — сколько читателей сейчас внутри.
- `isActiveWriterPresent` — есть ли сейчас писатель (0/1).
- `waitingWriters` — сколько писателей ждёт входа.
- `mutex` — обычная взаимная блокировка, чтобы все изменения состояния были атомарны.
- `readCondition` и `writeCondition` — очереди ожидания (conditions), чтобы разбудить нужный тип потоков.

> Без reentrancy значит, что один поток не должен “захватывать lock повторно” — упрощает логику: вы не храните hold-count по потокам, достаточно общей статистики.

---

### 2) Захват **read lock** (ключевое правило writer-preference)
Поток читателя:
1. Берёт `mutex`.
2. Ждёт, пока выполняется хотя бы одно:
    - `isActiveWriterPresent == true` (писатель уже внутри),
    - **или** `waitingWriters > 0` (есть писатели, которые ждут).
3. Когда условия снялись: увеличивает `activeReaders` и входит.
4. Отпускает `mutex`.

**Смысл:** как только появляется ожидающий писатель, новые читатели больше не “обгоняют” его — писатель получит шанс.

---

### 3) Захват **write lock**
Поток писателя:
1. Берёт `mutex`.
2. Увеличивает `waitingWriters`.
3. Ждёт, пока выполняется хотя бы одно:
    - `isActiveWriterPresent == true`,
    - `activeReaders > 0` (есть активные читатели).
4. Когда можно: уменьшает `waitingWriters`, ставит `isActiveWriterPresent = true` и входит.
5. Отпускает `mutex`.

---

### 4) `unlock` read: когда будить писателя
Когда читатель выходит:
1. Берёт `mutex`.
2. Уменьшает `activeReaders`.
3. Если `activeReaders == 0`, значит писателю больше нечего ждать из-за читателей:
    - будим писателей (`writeCondition`).
4. Отпускает `mutex`.

---

### 5) `unlock` write: кого будить дальше
Когда писатель выходит:
1. Берёт `mutex`.
2. Снимает `isActiveWriterPresent` (ставит `false`).
3. Дальше стратегию определяем writer-preference:
    - если `waitingWriters > 0`, будим писателей (чтобы очередь писателей не была “сломана” читателями),
    - иначе будим читателей (они могут все зайти параллельно).

Обычно в таких реализациях удобно будить **все** потоки одного типа (broadcast), но суть не в механике, а в выборе “кому давать первый шанс”.

---

## 6) Важные тонкости
1. **Всегда проверяй условия в цикле** при ожидании. Condition может “проснуться” без причины (spurious wakeup).
2. **unlock должен реально менять состояние так, чтобы следующий поток мог пройти** — иначе легко получить зависания.
3. **Инварианты (проверяй мысленно)**:
    - если `isActiveWriterPresent == true`, то `activeReaders` должно быть `0`;
    - если `waitingWriters > 0`, новые read-lock не должны проходить (по правилу writer-preference).
 твою форму я опишу, где именно лучше разместить поля и какие гарантии (например, про interruptibility) тебе стоит поддержать.
