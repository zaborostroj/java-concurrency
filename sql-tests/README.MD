# SQL Tests Module

Модуль предназначен для написания и проверки SQL-запросов в изолированной среде.

## Концепция

1. **Testcontainers**: Для каждого запуска тестов автоматически поднимается реальная база данных PostgreSQL в Docker-контейнере. Это гарантирует идентичность окружения и чистоту данных.
2. **Миграции БД**: Структура таблиц и начальные данные управляются через Liquibase. Файлы миграций находятся в `src/test/resources/db/changelog`.
3. **Native Query**: В тестах используется чистый SQL и JDBC. Это позволяет тестировать именно синтаксис и логику запросов без влияния ORM (Object-Relational Mapping).
4. **Один запрос — один тест**: Каждый метод теста проверяет один конкретный SQL-запрос.
5. **Минимализм**: В модуле специально не используются Spring, Hibernate или другие усложняющие фреймворки. Это ускоряет запуск и позволяет сосредоточиться на работе с базой данных напрямую.

## Как запускать тесты

### Предварительные требования
- Установленный и запущенный **Docker** (необходим для работы Testcontainers).
- Java 17 или выше.
- Maven.

### Запуск из терминала
Для запуска всех тестов в этом модуле выполните команду из корня проекта:
```bash
mvn test -pl sql-tests
```
Или из самой директории `sql-tests`:
```bash
mvn test
```

### Запуск из IDE (IntelliJ IDEA)
1. Перейдите в файл `src/test/java/org/example/sql/BasicSqlQueryTest.java`.
2. Нажмите кнопку **Run** (зеленый треугольник) напротив имени класса или конкретного теста.

## Структура проекта
- `src/test/java` — классы с тестами.
- `src/test/resources/db/changelog` — скрипты Liquibase для создания схем и наполнения данными.
- `pom.xml` — конфигурация сборки и зависимости (Testcontainers, PostgreSQL driver, Liquibase, JUnit 5).

### Индексы

##### Что такое индекс?
Индекс — это вспомогательная структура данных в базе данных, предназначенная для повышения скорости поиска и извлечения записей из таблицы. По аналогии с предметным указателем в книге, индекс позволяет СУБД быстро находить нужные строки, не перебирая всё содержимое таблицы целиком.

Индексы создаются для определенных колонок и хранят значения этих колонок в отсортированном или ином структурированном виде вместе с указателями на соответствующие физические записи. Однако за ускорение чтения приходится платить дополнительным дисковым пространством и снижением производительности при операциях записи.

##### Как работает индекс?
Индекс работает по принципу "ключ — адрес". Он хранит значения индексируемого столбца в упорядоченном виде. Когда выполняется запрос с условием поиска (например, `WHERE id = 100`), база данных сначала обращается к индексу, быстро находит там значение 100 за минимальное количество операций и получает ссылку (ROWID или адрес) на конкретное место на диске, где лежит вся строка.

Без индекса СУБД была бы вынуждена выполнять Full Table Scan — последовательно считывать каждую страницу данных с диска и проверять каждую строку на соответствие условию. Индекс сводит эту задачу к логарифмическому или константному времени поиска, что критически важно при работе с миллионами записей.

##### B-tree индекс
B-tree (Balanced Tree) — это наиболее распространенный тип индекса, представляющий собой сбалансированное дерево поиска. В нем данные хранятся в виде иерархии: корневой узел, промежуточные узлы и листовые узлы. Такая структура гарантирует, что путь от корня к любому значению имеет одинаковую длину, что обеспечивает стабильную производительность.

Главное преимущество B-tree заключается в его универсальности. Он эффективно поддерживает не только поиск по точному совпадению, но и поиск по диапазонам (`BETWEEN`, `>`, `<`), а также сортировку данных. Большинство современных СУБД (PostgreSQL, MySQL, Oracle) используют B-tree как тип индекса по умолчанию.

##### Hash index
Hash-индекс основан на использовании хэш-таблицы. При индексации значения колонки пропускаются через хэш-функцию, и результат (хэш-код) сопоставляется с указателем на строку. Это позволяет находить данные практически мгновенно, так как поиск сводится к одному вычислению хэша.

Однако у Hash-индексов есть существенные ограничения. Они идеально работают только для сравнения на точное равенство (`=`). Они не поддерживают поиск по диапазонам, сортировку или частичное совпадение строк, так как хэш-функция полностью перемешивает порядок данных. Кроме того, они хуже справляются с коллизиями при большом объеме данных.

##### Clustered index
Кластерный индекс определяет физический порядок хранения самих данных в таблице. В отличие от обычных индексов, листовые узлы кластерного индекса содержат не просто ссылки, а сами строки данных. Это означает, что таблица физически отсортирована по ключу этого индекса.

Поскольку данные могут быть физически упорядочены только одним способом, у таблицы может быть только один кластерный индекс (обычно это Primary Key). Поиск по такому индексу максимально эффективен, так как после нахождения ключа базе данных не нужно делать дополнительный переход за самой строкой — она уже находится в узле дерева.

##### Non-clustered index
Некластерный индекс (или вторичный индекс) — это структура, которая хранится отдельно от данных таблицы. Он содержит копию индексируемых колонок и указатель (ссылку) на реальную строку в таблице. В PostgreSQL все индексы являются некластерными, а в MySQL (InnoDB) некластерные индексы хранят значение первичного ключа.

Вы можете создать множество некластерных индексов для одной таблицы. При поиске по такому индексу СУБД сначала находит ключ в индексе, а затем делает дополнительную операцию чтения (Lookup), чтобы достать остальные колонки из таблицы. Если все необходимые данные уже есть в самом индексе, такая операция называется "Covering Index" и работает быстрее.

##### Unique index
Уникальный индекс — это специальный тип индекса, который помимо ускорения поиска накладывает ограничение целостности: все значения в индексируемой колонке должны быть уникальными. Попытка вставить дубликат приведет к ошибке.

Чаще всего уникальные индексы создаются автоматически для первичных ключей (`PRIMARY KEY`) и колонок с ограничением `UNIQUE`. С точки зрения производительности они работают так же, как и обычные индексы, но дают оптимизатору дополнительную информацию: он знает, что после нахождения одного совпадения поиск можно прекратить.

##### Composite index
Составной индекс (Composite Index) строится по двум или более колонкам одновременно. Он полезен в случаях, когда в условиях `WHERE` часто используются несколько полей вместе (например, `WHERE last_name = 'Ivanov' AND first_name = 'Ivan'`).

Порядок колонок в составном индексе критически важен. Он определяет, как данные будут отсортированы внутри индекса. Правильно спроектированный составной индекс может значительно ускорить сложные запросы, но он менее универсален, чем несколько одиночных индексов, из-за правила левого префикса.

##### leftmost prefix rule
Правило левого префикса гласит, что составной индекс по колонкам `(A, B, C)` может быть использован для поиска по `(A)`, `(A, B)` или `(A, B, C)`. Однако он не поможет, если в условии указаны только `(B)` или `(C)`, так как данные внутри индекса отсортированы сначала по `A`, затем по `B` и так далее.

Это можно сравнить с телефонным справочником, отсортированным по связке "Фамилия + Имя". Вы легко найдете всех Ивановых или конкретного Иванова Ивана. Но если вам нужно найти всех людей с именем "Иван", справочник вам не поможет — имена разбросаны по всем страницам, и придется просматривать его целиком.

##### Почему индекс ускоряет SELECT?
Индекс превращает линейную сложность поиска $O(N)$ в логарифмическую $O(\log N)$ (для B-tree). Это означает, что при увеличении таблицы в 1000 раз количество операций для поиска увеличится лишь незначительно. База данных считывает всего несколько блоков индекса вместо сканирования миллионов строк с диска.

Кроме того, индексы сокращают объем ввода-вывода (I/O), который является самым узким местом в производительности БД. Запрос может быть выполнен быстрее еще и потому, что индексы часто помещаются в оперативную память (Buffer Pool), что позволяет избежать медленных обращений к дисковому накопителю.

##### Почему индекс замедляет INSERT?
Операция вставки требует не только добавления строки в саму таблицу, но и обновления всех существующих индексов. Для каждого индекса СУБД должна найти правильное место в дереве (или хэш-таблице), вставить туда новый ключ и, если нужно, выполнить балансировку дерева.

Чем больше индексов на таблице, тем больше "накладных расходов" на каждую операцию изменения данных. В случае массовой вставки данных (Bulk Load) часто рекомендуется сначала удалить индексы, загрузить данные, а затем пересоздать их заново — это оказывается быстрее, чем обновлять индексы при каждой вставке строки.

##### Почему слишком много индексов плохо?
Избыточное количество индексов создает три основные проблемы: существенное замедление операций записи (`INSERT`, `UPDATE`, `DELETE`), повышенное потребление дискового пространства и усложнение работы оптимизатора запросов. Каждый индекс — это отдельный объект, который нужно хранить и обслуживать.

Когда индексов слишком много, оптимизатор может тратить значительное время на выбор лучшего плана выполнения или, в худшем случае, выбрать неоптимальный индекс. Хорошая практика — держать только те индексы, которые реально используются в критически важных или часто выполняемых запросах.

##### Почему запрос не использует индекс?
Существует несколько причин, по которым оптимизатор может проигнорировать индекс. Самая частая — низкая селективность: если значение, которое вы ищете, встречается в 50% строк таблицы, СУБД решит, что Full Table Scan будет дешевле, чем прыжки между индексом и таблицей.

Также индекс не сработает, если колонка обернута в функцию (например, `WHERE UPPER(name) = 'ADMIN'`), если не соблюдается правило левого префикса в составном индексе или если типы данных в условии и в таблице не совпадают, вызывая неявное приведение типов. Наконец, статистика по таблице может быть устаревшей, вводя оптимизатор в заблуждение.

##### Что такое full table scan?
Full Table Scan (FTS) — это метод доступа к данным, при котором СУБД последовательно считывает каждую строку из таблицы, чтобы проверить её на соответствие заданным условиям. Это самый "тяжелый" способ поиска, требующий максимального количества операций чтения с диска.

Хотя FTS обычно считается признаком плохой оптимизации, он не всегда плох. На маленьких таблицах (в несколько страниц) полное сканирование может быть быстрее, чем работа с индексами. Также FTS эффективен при операциях, где нужно обработать или вернуть большую часть строк таблицы (более 10-20%), так как последовательное чтение блоков с диска быстрее, чем случайное чтение по ссылкам из индекса.

##### Когда индекс бесполезен?
Индексы практически бесполезны на очень маленьких таблицах, где чтение всей таблицы занимает меньше времени, чем обращение к индексу. Также они не приносят пользы на колонках с низкой кардинальностью (малым количеством уникальных значений), например, на поле "пол" или "статус" с двумя вариантами, так как они не позволяют эффективно отсеивать строки.

Еще один случай — когда запрос возвращает слишком много данных (например, 80% таблицы). В этой ситуации использование индекса только замедлит процесс из-за постоянных переходов к основной таблице (Random I/O). Также индекс бесполезен, если условия запроса не позволяют его задействовать (использование функций, оператор `LIKE` с процентом в начале или поиск по не-префиксным частям составного индекса).

### Query optimization

##### Что такое EXPLAIN?
`EXPLAIN` — это фундаментальный инструмент для анализа производительности запросов. Он показывает план выполнения (Query Plan), который строит оптимизатор базы данных. План представляет собой дерево операций, таких как сканирование таблиц, использование индексов и алгоритмы соединений. Понимание этого плана позволяет точно определить узкие места: где не хватает индексов, где происходит избыточное чтение данных или где СУБД ошибочно выбирает неэффективный способ объединения таблиц.

Пример в PostgreSQL:
```sql
EXPLAIN ANALYZE 
SELECT * FROM orders 
WHERE user_id = 500 AND status = 'COMPLETED';
```
Вывод покажет, использовался ли индекс по `user_id` (`Index Scan`) или СУБД пришлось перебирать все заказы (`Seq Scan`). Параметр `ANALYZE` крайне важен, так как он заставляет базу данных действительно выполнить запрос и предоставить реальную статистику (`actual time`, `actual rows`), а не только теоретические догадки оптимизатора. В выводе также можно увидеть `cost`, где первое число — затраты на получение первой строки, а второе — на получение всех строк.

##### Как искать медленный запрос?
Основной способ обнаружения проблемных запросов — использование логов медленных запросов (**Slow Query Log**). В настройках СУБД (например, `log_min_duration_statement` в PostgreSQL или `long_query_time` в MySQL) задается порог времени, после которого запрос считается медленным и записывается в лог вместе с параметрами выполнения. Это позволяет собрать список реальных запросов, которые тормозят приложение "в полях".

Для более глубокого анализа в PostgreSQL существует расширение `pg_stat_statements`. Оно агрегирует статистику по всем типам запросов: сколько раз вызывались, среднее и максимальное время выполнения, объем прочитанных данных. Это помогает выявить не только одиночные "тяжелые" запросы, но и те, которые работают быстро, но вызываются слишком часто (проблема N+1 или неоптимальная логика в коде), создавая паразитную нагрузку на CPU и диск.

##### Почему JOIN может быть медленным?
Чаще всего `JOIN` работает медленно из-за **отсутствия индексов** на столбцах, по которым происходит объединение таблиц (обычно это Foreign Keys). Без индексов СУБД вынуждена использовать алгоритм `Nested Loop` со вложенным сканированием таблицы для каждой строки основной таблицы, что превращает сложность запроса в $O(N \times M)$. Если таблицы большие, такой запрос может выполняться минуты.

Другая причина — **огромное количество соединяемых таблиц**. С каждым новым `JOIN` количество возможных планов выполнения растет экспоненциально, и оптимизатору становится сложнее найти лучший путь. Также на скорость влияют несовпадение типов данных (вызывающее неявное приведение типов и игнорирование индексов) и нехватка оперативной памяти для временных таблиц при использовании `Hash Join`, из-за чего данные начинают сбрасываться на медленный диск.

##### Почему OFFSET может быть дорогим?
Проблема `OFFSET` заключается в том, что СУБД должна просканировать и отбросить все записи, предшествующие нужному результату. При выполнении `SELECT ... LIMIT 10 OFFSET 1000000` база данных не может "перепрыгнуть" сразу к миллионной строке; она обязана прочитать (и часто отсортировать) все 1 000 000 строк, чтобы понять, где начинается нужная порция данных.

С ростом номера страницы (глубины пагинации) нагрузка на дисковую подсистему и процессор растет линейно. Для решения этой проблемы используют **курсорную пагинацию (Keyset Pagination)**. Вместо смещения используется фильтрация по последнему полученному значению, например: `WHERE id > last_id LIMIT 10`. В этом случае база данных мгновенно находит нужную точку входа через индекс, и скорость запроса остается стабильной независимо от общего количества данных.

##### N+1 problem
Проблема N+1 возникает, когда код сначала запрашивает список из N объектов, а затем в цикле для каждого объекта делает еще один запрос для получения связанных данных. В итоге вместо одного эффективного запроса с `JOIN` база данных получает 1 (основной) + N (дополнительных) запросов. Например: получить 50 постов блога, а затем 50 отдельными запросами получить авторов для каждого поста.

Это критически снижает производительность из-за огромного количества "сетевых задержек" (network round-trips) и накладных расходов СУБД на парсинг и выполнение каждого мелкого запроса. Проблема часто прячется внутри ORM, которые лениво (Lazy Load) подгружают связи. Чтобы этого избежать, используют **Eager Loading** (загрузка через `JOIN` или предварительная подгрузка связанных ID через `IN (...)`), объединяя N+1 запрос в один или два.

### Java/backend related

##### Lazy loading
Lazy loading (ленивая загрузка) — это стратегия загрузки данных, при которой связанные объекты не загружаются из базы данных до тех пор, пока к ним не произойдет первое обращение в коде. Например, если у вас есть объект "Пользователь" со списком "Заказов", при ленивой загрузке Hibernate загрузит только данные пользователя, а вместо списка заказов подставит прокси-объект. Реальный SQL-запрос к таблице заказов будет выполнен только в момент вызова метода `user.getOrders()`.

Основное преимущество этого подхода — экономия ресурсов памяти и сокращение времени выполнения основного запроса, так как мы не тянем лишние данные, которые могут не понадобиться. Однако ленивая загрузка часто становится причиной исключений `LazyInitializationException`, если обращение к данным происходит вне открытой транзакции или сессии Hibernate, а также провоцирует проблему N+1 при итерации по списку объектов.

##### Eager loading
Eager loading (жадная загрузка) — это стратегия, при которой связанные данные загружаются из базы данных сразу вместе с основным объектом одним или несколькими запросами. В Hibernate это настраивается через параметр `fetch = FetchType.EAGER`. В этом случае при загрузке "Пользователя" СУБД сразу вернет и его данные, и данные всех его "Заказов", обычно используя `LEFT JOIN` или отдельный быстрый запрос по идентификатору.

Жадная загрузка полезна, когда вы точно знаете, что связанные данные понадобятся вам в 100% случаев. Она предотвращает появление `LazyInitializationException` и проблемы N+1. Однако её бесконтрольное использование может привести к "взрыву данных": если у объекта много связей, помеченных как Eager, один простой запрос может превратиться в монструозное соединение десятка таблиц, что создаст огромную нагрузку на память и существенно замедлит работу приложения.

##### Как Hibernate вызывает N+1?
В Hibernate проблема N+1 чаще всего возникает при использовании `FetchType.LAZY` (который является стандартом для коллекций) в сочетании с итерацией по списку сущностей. Когда вы выполняете запрос `session.createQuery("from User").list()`, Hibernate делает 1 запрос, чтобы получить список всех пользователей. Но если затем в цикле вы начинаете обращаться к заказам каждого пользователя (`user.getOrders().size()`), Hibernate вынужден для каждой итерации выполнять новый отдельный запрос в БД для получения заказов конкретного пользователя.

Парадоксально, но `FetchType.EAGER` тоже может вызвать N+1, если запрос выполняется через HQL или Criteria API без явного указания `JOIN FETCH`. В этом случае Hibernate сначала получит список идентификаторов основным запросом, а затем, увидев пометку Eager, начнет подгружать связи для каждого найденного объекта отдельными запросами. Это происходит потому, что стратегии загрузки в маппинге — это лишь "рекомендации", а способ выполнения конкретного запроса зависит от того, как он написан.

##### Как бороться с N+1?
Самый эффективный способ борьбы с N+1 — использование **Join Fetch** в HQL/JPQL или EntityGraph. Это позволяет в рамках одного конкретного бизнес-сценария указать ORM, что данные нужно подтянуть жадно через `JOIN`, игнорируя настройки ленивости в маппинге. Например: `SELECT u FROM User u JOIN FETCH u.orders`. Таким образом, вместо N+1 запроса мы всегда получаем ровно один.

Другой подход — использование **Batch Fetching** (аннотация `@BatchSize`). Вместо того чтобы загружать связи по одной, Hibernate будет подгружать их пачками (например, по 20 или 50 штук) через оператор `IN`. Это не убирает лишние запросы полностью, но сокращает их количество с N до N/BatchSize, что часто является приемлемым компромиссом. Также можно использовать `FetchMode.SUBSELECT`, который загружает все связанные данные одним дополнительным подзапросом для всего исходного набора данных.

### Транзакции

##### Что такое транзакция?
Транзакция — это логическая единица работы с базой данных, состоящая из одного или нескольких SQL-запросов. Она гарантирует, что либо все действия внутри неё будут успешно применены, либо ни одно из них не сохранится. Это критически важно для поддержания целостности данных, например, при переводе денег между счетами, когда списание и зачисление должны произойти одновременно.

Основные свойства транзакции описываются аббревиатурой ACID. Транзакции позволяют изолировать действия пользователей друг от друга и обеспечивают устойчивость системы к сбоям: если в середине процесса произойдет ошибка, БД просто вернется в исходное состояние.

##### BEGIN / COMMIT / ROLLBACK
Это команды управления жизненным циклом транзакции. `BEGIN` (или `START TRANSACTION`) помечает начало блока операций. С этого момента все изменения, вносимые в данные, считаются предварительными и не видны другим пользователям (в зависимости от уровня изоляции).

`COMMIT` подтверждает транзакцию, делая все изменения постоянными и доступными для других. `ROLLBACK` — это команда отмены: она сбрасывает все незавершенные изменения текущей транзакции, возвращая базу данных в то состояние, в котором она была до выполнения `BEGIN`.

##### Что такое ACID?
ACID — это набор из четырех требований к транзакционной системе, гарантирующих надежность данных. **Atomicity (Атомарность)** гарантирует, что транзакция будет выполнена полностью или не выполнена совсем. **Consistency (Согласованность)** обеспечивает переход базы из одного корректного состояния в другое, не нарушая бизнес-правила и ограничения (constraints).

**Isolation (Изолированность)** делает так, что параллельные транзакции не влияют друг на друга, как если бы они выполнялись последовательно. **Durability (Стойкость)** гарантирует, что если транзакция была закоммичена, её результат не пропадет даже при внезапном выключении сервера или сбое питания.

### Isolation levels

##### Read uncommitted
Это самый низкий уровень изоляции, при котором транзакция может видеть изменения, внесенные другими транзакциями, которые еще не были закоммичены. Это обеспечивает максимальную скорость работы, так как блокировки практически не используются, но делает данные крайне ненадежными.

На этом уровне возможна аномалия "Dirty read" (грязное чтение). В современных промышленных системах этот уровень используется крайне редко, так как он не дает никаких гарантий целостности, и многие СУБД (например, PostgreSQL) даже при его указании фактически используют более строгий уровень.

##### Read committed
На этом уровне транзакция видит только те данные, которые были закоммичены до момента выполнения конкретного запроса на чтение. Это уровень изоляции по умолчанию во многих популярных СУБД, включая PostgreSQL и Oracle. Он предотвращает "Dirty read", но допускает аномалии при повторном чтении.

Если в процессе вашей транзакции другая транзакция изменит и закоммитит строку, то ваш повторный запрос увидит уже новые данные. Это явление называется "Non-repeatable read". Тем не менее, `Read committed` является хорошим балансом между производительностью и консистентностью для большинства приложений.

##### Repeatable read
Этот уровень гарантирует, что если вы прочитали строку в начале транзакции, то при повторном чтении в этой же транзакции вы получите абсолютно те же самые данные, даже если другие транзакции успели их изменить и закоммитить. Это достигается за счет создания снимка (snapshot) данных в начале транзакции.

Уровень предотвращает "Dirty read" и "Non-repeatable read", но в некоторых СУБД (например, MySQL InnoDB) на этом уровне все еще возможны "Phantom reads" — появление новых строк, добавленных другими транзакциями. В PostgreSQL реализация `Repeatable read` более строгая и защищает также и от фантомных чтений.

##### Serializable
Самый строгий уровень изоляции, обеспечивающий полную имитацию последовательного выполнения транзакций. База данных гарантирует, что результат параллельного выполнения группы транзакций будет точно таким же, как если бы они выполнялись строго одна за другой в определенном порядке.

Для этого СУБД отслеживает все зависимости между данными и, если обнаруживает риск нарушения целостности, прерывает конфликтующие транзакции с ошибкой сериализации (в этом случае приложение должно повторить транзакцию). Это самый безопасный, но и самый "медленный" уровень из-за накладных расходов на проверки.

### Аномалии

##### Dirty read
Грязное чтение (Dirty read) — это ситуация, когда транзакция читает данные, измененные другой транзакцией, которая еще не была закоммичена. Если вторая транзакция в итоге выполнит `ROLLBACK`, то первая транзакция окажется в ситуации, когда она обработала данные, которых никогда официально не существовало в базе.

Это опасно для бизнес-логики: например, система может принять решение о выдаче товара на основе "грязной" записи о пополнении баланса, которая через секунду будет отменена из-за ошибки в банковском шлюзе.

##### Non-repeatable read
Неповторяющееся чтение (Non-repeatable read) возникает, когда транзакция читает одну и ту же строку дважды, но получает разные значения, так как между этими чтениями другая транзакция изменила эту строку и успешно закоммитила изменения.

Проблема здесь не в ошибочности данных (они закоммичены), а в непредсказуемости поведения внутри одной транзакции. Если ваша логика предполагает, что данные не должны меняться в процессе обработки (например, при расчете сложного отчета), этот уровень может привести к противоречивым результатам.

##### Phantom read
Фантомное чтение (Phantom read) похоже на неповторяющееся чтение, но относится не к изменению существующих строк, а к изменению набора строк, попадающих под фильтр. Например, вы считаете сумму всех заказов, а в это время другая транзакция добавляет новый заказ. Повторный запрос вернет другую сумму.

Такие "строки-призраки" могут нарушить отчетность или логику массовой обработки. Уровень изоляции `Serializable` полностью решает эту проблему, а в некоторых СУБД (например, PostgreSQL) она решается и на уровне `Repeatable read`.

##### Lost update
Потерянное обновление (Lost update) случается, когда две транзакции одновременно читают одну и ту же строку, затем обе её изменяют и пытаются сохранить. В итоге транзакция, которая закоммитилась последней, просто затирает изменения первой транзакции, и данные первой транзакции бесследно исчезают.

Типичный пример — конкурентное списание баланса. Обе транзакции прочитали баланс 100, вычли по 10 и сохранили 90. В итоге вместо 80 на счету осталось 90. Эта аномалия решается с помощью блокировок (оптимистичных или пессимистичных) или высоких уровней изоляции.

### Locking

##### Что такое optimistic lock?
Оптимистичная блокировка — это подход, при котором база данных не блокирует строку при чтении. Вместо этого предполагается, что конфликты случаются редко. Для контроля используется дополнительная колонка (обычно `version` или `timestamp`). При обновлении проверяется, не изменилась ли версия с момента чтения.

Если версия совпадает, данные сохраняются, а версия инкрементируется. Если версия уже другая — значит, кто-то другой успел изменить данные, и транзакция выбрасывает ошибку (например, `OptimisticLockException`). Этот подход не нагружает БД блокировками и отлично подходит для систем с большим количеством чтений.

##### Что такое pessimistic lock?
Пессимистичная блокировка — это подход, основанный на принципе "лучше перестраховаться". Как только транзакция читает данные, она захватывает на них блокировку, предотвращая любые изменения этих данных другими транзакциями до завершения текущей. Другие процессы будут ждать (висеть в очереди), пока блокировка не будет снята.

В SQL это часто реализуется через конструкцию `SELECT ... FOR UPDATE`. Это гарантирует абсолютную консистентность, но сильно снижает пропускную способность системы, так как параллельные процессы простаивают в ожидании ресурсов.

##### Когда использовать optimistic?
Оптимистичную блокировку стоит выбирать в ситуациях с низкой конкуренцией на запись (Low Contention), когда вероятность того, что два пользователя одновременно изменят одну строку, невелика. Это стандарт для веб-приложений, где пользователи долго читают данные с экрана перед нажатием кнопки "Сохранить".

Она также идеальна для длительных бизнес-процессов, где физически невозможно держать транзакцию БД открытой все время (например, пока пользователь заполняет анкету). Оптимистичная блокировка масштабируется лучше, так как не расходует ресурсы сервера на поддержание живых блокировок в памяти.

##### Когда pessimistic?
Пессимистичная блокировка незаменима при высокой конкуренции на запись (High Contention), когда конфликты происходят постоянно и частые откаты транзакций (как в случае с optimistic) будут обходиться слишком дорого пользователям и системе.

Также её используют в критических финансовых операциях, где недопустимы даже кратковременные несоответствия или где нужно гарантировать выполнение операции "здесь и сейчас" без повторных попыток со стороны приложения. Она проще в реализации для сложных пакетных обработок данных.

##### Row lock
Row-level locking (блокировка на уровне строки) — это механизм, при котором СУБД блокирует только конкретные строки, задействованные в запросе. Это позволяет другим транзакциям свободно работать с остальными строками той же таблицы.

Это самый гранулярный вид блокировки, который обеспечивает максимальную параллельность работы пользователей. Современные СУБД (PostgreSQL, MySQL InnoDB) используют именно этот тип блокировки по умолчанию при операциях `UPDATE` или `DELETE`.

##### Table lock
Table-level locking (блокировка на уровне таблицы) — это механизм, при котором блокируется вся таблица целиком. Пока одна транзакция удерживает блокировку, ни одна другая транзакция не может изменить (а иногда и прочитать) ни одну строку в этой таблице.

Это крайне неэффективно для высоконагруженных систем, так как выстраивает все процессы в одну очередь. Однако такие блокировки полезны при выполнении сервисных операций, таких как изменение структуры таблицы (`ALTER TABLE`), очистка данных (`TRUNCATE`) или массовый импорт, когда нужно гарантировать отсутствие любых помех.

##### SELECT FOR UPDATE
Это SQL-конструкция, которая сообщает базе данных: "Я читаю эти строки и собираюсь их обновить, заблокируй их для меня прямо сейчас". Она превращает обычное чтение в пессимистичную блокировку. Другие транзакции не смогут изменить эти строки или вызвать для них `FOR UPDATE`, пока вы не сделаете `COMMIT` или `ROLLBACK`.

Это критически важно для реализации логики "проверил и обновил" (Check-then-Act) в конкурентной среде. Например, чтобы убедиться, что билетов на рейс все еще достаточно, перед тем как оформить бронь, предотвращая продажу одного билета двум разным людям.

##### Deadlock
Deadlock (взаимная блокировка) — это тупиковая ситуация, когда две транзакции ждут освобождения ресурсов, захваченных друг другом. Например, транзакция А заблокировала строку 1 и хочет заблокировать строку 2. В это же время транзакция Б заблокировала строку 2 и хочет заблокировать строку 1. Они будут ждать вечно.

СУБД автоматически обнаруживает такие ситуации (deadlock detection), выбирает одну из транзакций (обычно "самую дешевую" для отката) в качестве жертвы, прерывает её и делает `ROLLBACK`, позволяя второй транзакции продолжить работу.

##### Как избежать deadlock?
Самый простой и эффективный способ — всегда обращаться к ресурсам в **строгом и едином порядке**. Если все транзакции будут обновлять строки всегда по возрастанию их `ID`, дедлок станет физически невозможен.

Также помогают: сокращение длительности транзакций (меньше времени на захват ресурсов), избегание интерактивного взаимодействия с пользователем внутри транзакции, использование таймаутов блокировок и минимизация количества блокируемых данных (использование индексов, чтобы блокировать конкретные строки, а не диапазоны).

### MVCC

##### Что такое MVCC?
MVCC (Multi-Version Concurrency Control) — это метод управления конкурентным доступом, при котором база данных хранит несколько версий одной и той же строки. Вместо того чтобы блокировать данные при записи, СУБД создает новую версию строки, помечая старую как устаревшую.

Каждая транзакция видит тот "снимок" данных, который был актуален на момент её начала. Это позволяет СУБД обрабатывать сотни параллельных запросов без взаимных блокировок. Этот подход используется в PostgreSQL, Oracle, MySQL (InnoDB) и SQL Server.

##### Почему чтение не блокирует запись?
Благодаря MVCC, читающие транзакции работают со своей (старой) версией данных, в то время как пишущая транзакция создает новую версию в другом месте. Они не пересекаются физически, поэтому читатели никогда не ждут писателей, а писатели никогда не ждут читателей.

Это кардинально повышает производительность системы. Старые версии строк, которые больше не нужны ни одной активной транзакции, позже удаляются специальными процессами (например, `VACUUM` в PostgreSQL), чтобы освободить дисковое пространство.

### Java/Spring

##### Что делает @Transactional
Аннотация `@Transactional` в Spring автоматизирует управление транзакциями. Она избавляет разработчика от необходимости вручную писать `BEGIN`, `COMMIT` и `ROLLBACK`. Spring создает прокси-объект вокруг вашего бина, который открывает транзакцию перед выполнением метода и закрывает её после завершения.

Если метод завершается успешно, выполняется `COMMIT`. Если внутри метода выбрасывается исключение, Spring автоматически инициирует `ROLLBACK`. Также аннотация гарантирует, что все операции внутри метода (даже в разных репозиториях) будут использовать одно и то же соединение с БД и выполняться в рамках одной транзакции.

##### propagation
Настройка `propagation` (распространение) определяет, как транзакция будет вести себя, если она вызывается внутри уже существующей транзакции. Самый частый вариант — `REQUIRED` (по умолчанию): использовать текущую транзакцию или создать новую, если её нет.

Другие важные уровни: `REQUIRES_NEW` (всегда создает новую транзакцию, приостанавливая текущую), `MANDATORY` (требует наличия транзакции, иначе ошибка) и `NEVER` (запрещает транзакции). Правильный выбор propagation критичен при реализации вложенной логики, чтобы ошибка в одном месте не привела к неожиданному откату всей цепочки действий.

##### isolation в Spring
Параметр `isolation` в `@Transactional` позволяет задать уровень изоляции для конкретного метода, переопределяя настройки базы данных по умолчанию. Можно выбрать один из стандартных уровней: `READ_COMMITTED`, `REPEATABLE_READ` и т.д.

Spring транслирует эту настройку в специфичные команды для драйвера БД при открытии транзакции. Это полезно, когда для конкретного тяжелого отчета вам нужен уровень `REPEATABLE_READ`, в то время как все остальное приложение работает на стандартном `READ_COMMITTED`.

##### rollback behavior
По умолчанию Spring делает откат транзакции (`rollback`) только при возникновении `RuntimeException` или `Error`. Проверяемые исключения (`Checked Exceptions`) не вызывают автоматический откат, так как они считаются ожидаемыми бизнес-ситуациями.

Это поведение можно настроить с помощью параметров `rollbackFor` (указать, на каких исключениях откатываться) и `noRollbackFor` (на каких — нет). Хорошей практикой считается явное указание `rollbackFor = Exception.class`, если вы хотите гарантировать откат при любой непредвиденной ситуации в коде.

### Репликация

##### Что такое replication?
Репликация — это процесс копирования данных с одного сервера базы данных (мастера) на один или несколько других серверов (реплик). Это позволяет повысить отказоустойчивость системы: если основной сервер выйдет из строя, данные сохранятся на репликах. Также репликация используется для масштабирования операций чтения, распределяя нагрузку между несколькими узлами.

##### master/slave vs leader/follower
Эти термины описывают роли узлов в кластере. Мастер (или лидер) принимает все запросы на изменение данных (запись), а затем распространяет эти изменения на реплики (слэйвов или фолловеров). Современное техническое сообщество чаще использует термины leader/follower как более нейтральные, но концептуально они описывают одну и ту же иерархическую структуру управления данными.

##### read replica
Читающая реплика — это узел базы данных, который содержит актуальную копию данных мастера и предназначен исключительно для выполнения запросов `SELECT`. Использование реплик для чтения позволяет разгрузить основной сервер от "тяжелых" отчетов и аналитики, обеспечивая высокую скорость ответа основного приложения на операции записи.

##### synchronous vs asynchronous replication
При синхронной репликации мастер ждет подтверждения от реплики о записи данных, прежде чем ответить клиенту об успешном выполнении транзакции. Это гарантирует отсутствие потери данных, но увеличивает время ответа (latency). При асинхронной репликации мастер подтверждает запись сразу, а данные передаются на реплики в фоновом режиме, что быстрее, но создает риск потери последних транзакций при аварии.

##### replication lag
Репликационный лаг — это задержка во времени между моментом записи данных на мастер и моментом их появления на реплике. Он возникает из-за нагрузки на сеть, медленной дисковой подсистемы реплики или большого объема транзакций. Большой лаг может приводить к тому, что пользователь, записав данные и сразу попытавшись их прочитать с реплики, увидит устаревшее состояние (эффект "пропавших" данных).

### Partitioning/Sharding

##### Что такое partitioning?
Партиционирование — это разделение одной большой таблицы на более мелкие, управляемые части (секции) на уровне одной базы данных. Для пользователя и приложения таблица выглядит как единое целое, но физически СУБД хранит данные в разных файлах. Это ускоряет работу с огромными объемами данных за счет исключения ненужных разделов при поиске (partition pruning).

##### Горизонтальное vs вертикальное partitioning
Горизонтальное партиционирование разделяет таблицу по строкам (например, заказы за разные годы в разных секциях). Вертикальное партиционирование разделяет таблицу по столбцам, вынося редко используемые или "тяжелые" поля (например, большие текстовые описания или BLOB) в отдельные таблицы. Оба метода направлены на уменьшение объема данных, которые СУБД должна считывать с диска за один раз.

##### Что такое sharding?
Шардирование — это метод горизонтального масштабирования, при котором данные распределяются между несколькими полностью независимыми серверами баз данных. Каждый такой сервер называется шардом и содержит только часть общего набора данных. В отличие от партиционирования, шарды обычно не знают о существовании друг друга, и логика распределения данных лежит на уровне приложения или специального middleware.

##### Когда шардировать?
К шардированию прибегают, когда возможности вертикального масштабирования (увеличения CPU/RAM) исчерпаны, а одна база данных перестает справляться с нагрузкой или объемом данных. Это крайняя мера, так как она значительно усложняет архитектуру проекта, затрудняет выполнение `JOIN` между шардами и поддержку транзакционной целостности.

##### Проблемы shard’ов
Основные сложности включают невозможность выполнения запросов с объединением данных из разных шардов (Cross-shard joins), трудности с обеспечением уникальности глобальных идентификаторов и проблему "горячих шардов", когда один узел оказывается перегружен данными или запросами сильнее других. Также крайне сложно проводить перебалансировку данных (resharding) при росте системы.

### Distributed systems

##### CAP theorem
Теорема CAP утверждает, что распределенная система может одновременно обладать не более чем двумя из трех свойств: **Consistency** (согласованность — все узлы видят одинаковые данные одновременно), **Availability** (доступность — каждый запрос получает ответ) и **Partition tolerance** (устойчивость к разделению — система продолжает работать при разрыве связи между узлами). В реальных сетях сбои неизбежны, поэтому выбор обычно стоит между CP или AP.

##### eventual consistency
Согласованность в конечном счете — это модель, гарантирующая, что если в систему перестанут поступать новые изменения, то через некоторое время все узлы придут к единому состоянию и будут возвращать актуальные данные. Это компромисс, используемый во многих NoSQL и высоконагруженных распределенных системах ради обеспечения доступности и низкой задержки.

##### consistency vs availability
Это классический выбор в условиях сетевого сбоя. Если вы выбираете согласованность (Consistency), вы должны отклонять запросы, если не можете гарантировать актуальность данных на всех узлах (система становится недоступной). Если вы выбираете доступность (Availability), узлы будут отвечать клиентам даже в условиях изоляции, но данные на них могут временно различаться.

##### split brain
"Разделение мозга" — это критическая ситуация в кластере, когда из-за потери связи узлы перестают видеть друг друга и каждая изолированная часть решает, что она теперь является главной. Это приводит к тому, что разные части системы начинают независимо принимать изменения, что вызывает конфликты и противоречивость данных. Для предотвращения этого используют алгоритмы консенсуса (Raft, Paxos) и механизмы кворума.

### Scaling

##### Вертикальное масштабирование
Это увеличение мощности одного сервера за счет добавления ресурсов: более мощного процессора, большего объема оперативной памяти или более быстрых SSD. Это самый простой способ, не требующий изменений в коде приложения. Однако у вертикального масштабирования есть физический и экономический потолок — топовые серверы стоят экспоненциально дороже.

##### Горизонтальное масштабирование
Это добавление новых серверов в систему. Для баз данных это реализуется через репликацию (для масштабирования чтения) или шардирование (для масштабирования записи). Этот подход теоретически бесконечен и позволяет строить системы на базе обычного, массового "железа", но требует сложной программной архитектуры для распределения нагрузки и управления данными.

##### Bottlenecks в БД
Узкие места базы данных обычно кроются в трех ресурсах: **Дисковый I/O** (медленное чтение/запись данных), **CPU** (сложные вычисления, сортировки, отсутствие индексов) и **Network** (передача больших объемов данных). Также часто проблемой становятся блокировки (Lock contention), когда транзакции стоят в очереди к одной строке, и неоптимальные настройки буферного пула, из-за чего БД не может эффективно кэшировать данные в памяти.

### NoSQL

##### Что такое NoSQL?
NoSQL (Not Only SQL) — это широкий термин, объединяющий различные системы управления базами данных, которые отличаются от традиционных реляционных СУБД (RDBMS). Они не используют табличную схему со строгими связями и часто предлагают гибкие модели данных, такие как документы, графы или пары "ключ-значение". NoSQL решения ориентированы на высокую производительность, масштабируемость и работу с неструктурированными или быстро меняющимися данными.

Такие базы данных часто отказываются от полной поддержки ACID (особенно Atomicity и Consistency) в пользу теоремы CAP, что позволяет им эффективно распределять данные по многим узлам. Это делает NoSQL идеальным выбором для Big Data, систем реального времени и облачных приложений, где горизонтальное масштабирование является критическим фактором.

##### Когда SQL не подходит?
Реляционные базы данных могут стать узким местом, когда данные не имеют четкой структуры или эта структура постоянно меняется (например, метаданные товаров с сотнями разных атрибутов). Также SQL может быть избыточен для простых операций "ключ-значение", где важна минимальная задержка, или когда требуется хранение огромных объемов данных (десятки и сотни терабайт), требующих легкого горизонтального масштабирования.

SQL также плохо справляется с глубоко вложенными иерархиями или сложными сетевыми связями, где количество JOIN-ов делает запросы слишком медленными и сложными. Если ваше приложение требует сверхвысокой доступности и готово пожертвовать мгновенной согласованностью данных (Strong Consistency) ради работы в распределенном кластере, NoSQL может быть более подходящим выбором.

##### Типы NoSQL
NoSQL базы данных обычно классифицируются по способу организации данных. Основные четыре типа: **Key-Value** (Redis, Amazon DynamoDB), **Document-oriented** (MongoDB, CouchDB), **Column-family** (Apache Cassandra, HBase) и **Graph** (Neo4j, ArangoDB). Каждый тип оптимизирован под конкретные задачи: от сверхбыстрого кэширования до анализа сложных социальных связей.

Выбор конкретного типа зависит от паттернов доступа к данным. Например, если данные ищутся по уникальному идентификатору, подойдет Key-Value. Если нужно хранить сложные объекты с вложенностью — Document. Для анализа взаимосвязей между сущностями — Graph. А для записи огромных потоков данных с последующим анализом по времени — Column-family.

##### key-value
Базы данных типа "ключ-значение" — это самая простая модель NoSQL, где данные хранятся как пары уникального ключа и соответствующего ему значения (которое для БД является непрозрачным набором байтов). Они работают аналогично хэш-таблице в памяти. Основные преимущества: экстремальная скорость работы и простота масштабирования.

Такие системы идеально подходят для хранения сессий пользователей, корзин в интернет-магазинах, конфигураций или в качестве кэширующего слоя. Яркие представители: Redis (часто используется как In-memory хранилище) и Amazon DynamoDB. Главный минус — невозможность выполнять сложные запросы по значениям, поиск возможен только по ключу.

##### document
Документоориентированные базы данных хранят данные в виде документов, обычно в форматах JSON, BSON или XML. В отличие от реляционных таблиц, документы в одной коллекции могут иметь разную структуру (схемы не фиксированы). Это позволяет легко добавлять новые поля без изменения всей базы.

Документы позволяют хранить связанные данные вместе в одном объекте, что избавляет от необходимости использовать JOIN. Это значительно ускоряет чтение сложных сущностей. Самыми популярными представителями являются MongoDB и CouchDB. Такие БД отлично подходят для каталогов товаров, контент-менеджмента и приложений с быстро меняющимися требованиями.

##### graph
Графовые базы данных используют теорию графов для хранения данных, где сущности представлены как узлы (nodes), а связи между ними — как ребра (edges). Оба могут иметь свои свойства. В отличие от других БД, связи здесь являются первоклассными сущностями, и переход по ним выполняется мгновенно, независимо от объема данных.

Они незаменимы для задач, где взаимосвязи важнее самих данных: социальные сети, рекомендательные движки (например, "вам может понравиться этот товар"), системы обнаружения мошенничества или логистика. Neo4j и ArangoDB — известные представители этого семейства. Использование SQL для таких задач потребовало бы множества рекурсивных JOIN-ов, что крайне неэффективно.

##### column-family
Базы данных семейств колонок (или ширококолоночные) хранят данные в колонках, а не в строках. Группы колонок (column families) хранятся физически вместе на диске. Это позволяет очень быстро считывать конкретные атрибуты миллионов записей и эффективно сжимать данные, так как значения в одной колонке часто похожи.

Такие БД, как Apache Cassandra или HBase, спроектированы для работы в огромных распределенных кластерах и обработки петабайт данных. Они отлично справляются с интенсивной записью и аналитическими запросами. Основные сценарии использования: хранение логов, метрик, истории транзакций и данных временных рядов (Time-series).

##### Когда выбрать SQL?
SQL стоит выбирать, когда данные имеют четкую, стабильную структуру и важна строгая целостность данных (ACID). Если бизнес-логика требует сложных аналитических запросов с объединением множества сущностей, SQL-оптимизаторы справятся с этим лучше. Транзакционность особенно важна в финансовых системах и при управлении заказами.

Также реляционные БД — это зрелая технология с огромным сообществом, мощными инструментами мониторинга и стандартизированным языком запросов. Если объем данных и нагрузка позволяют масштабироваться вертикально (или через чтение с реплик), SQL обычно является более надежным и предсказуемым выбором для большинства корпоративных приложений.

##### Когда выбрать NoSQL?
NoSQL — лучший выбор для проектов с неопределенной или часто меняющейся структурой данных, где важна скорость разработки и гибкость. Если ваше приложение должно обрабатывать огромные потоки данных (High Load) и требует легкого горизонтального масштабирования путем добавления новых узлов, NoSQL архитектура изначально спроектирована под эти задачи.

Также выбирайте NoSQL, если вашим приоритетом является высокая доступность (Availability) и низкая задержка, а небольшая временная несогласованность данных (Eventual Consistency) допустима. Например, в социальных сетях не страшно, если лайк под постом появится у друзей с задержкой в секунду, но критично, чтобы система работала без сбоев.

##### eventual consistency
Согласованность в конечном счете (Eventual Consistency) — это модель согласованности данных, при которой гарантируется, что если в систему перестанут поступать обновления, то через некоторое время все копии данных на разных узлах станут идентичными. Это фундаментальный компромисс в распределенных системах ради обеспечения высокой доступности.

В отличие от строгой согласованности, когда пользователь всегда видит самый последний результат записи, здесь чтение может вернуть устаревшее значение. Это характерно для многих NoSQL систем (например, Cassandra или DNS). Разработчики должны учитывать это поведение в логике приложения, используя, например, версионность или механизмы разрешения конфликтов.

### Базы и use cases

##### Redis — когда использовать?
Redis — это In-memory хранилище структур данных, которое чаще всего используется как высокопроизводительный кэш, брокер сообщений или хранилище сессий. Так как все данные находятся в оперативной памяти, операции выполняются за доли миллисекунды.

Его стоит использовать для задач, где скорость критична: хранение токенов авторизации, реализация лимитов запросов (Rate Limiting), очереди задач или real-time аналитика (например, счетчики просмотров). Redis также поддерживает сложные структуры: списки, множества, хэши и даже гео-индексы, что делает его мощным инструментом в дополнение к основной базе данных.

##### MongoDB — когда использовать?
MongoDB — это документоориентированная база данных, которую стоит выбирать, когда ваши данные лучше всего ложатся в JSON-подобную структуру. Она идеально подходит для приложений с гибкой схемой, где структура сущностей может отличаться от записи к записи.

Типичные кейсы: каталоги товаров со специфичными атрибутами, системы хранения пользовательских профилей, блоги, форумы и приложения для работы с контентом. Благодаря встроенным механизмам шардирования и репликации, MongoDB легко масштабируется под большие нагрузки, что делает её популярным выбором для современных веб-сервисов.

##### Apache Cassandra
Apache Cassandra — это распределенная база данных Column-family типа, созданная для работы с колоссальными объемами данных на сотнях и тысячах серверов. Она обладает уникальной архитектурой "без мастера" (Masterless), что означает отсутствие единой точки отказа и невероятную устойчивость к сбоям.

Её следует использовать, когда важна бесперебойная запись огромных потоков информации (логи, сенсоры IoT, финансовые транзакции) и требуется линейное масштабирование. Cassandra позволяет настраивать уровень согласованности для каждого запроса, что дает гибкость в балансе между скоростью и точностью данных.

##### cache vs DB
Основное различие между кэшем и базой данных заключается в их назначении и характеристиках хранения. База данных является "источником истины", обеспечивая долгосрочное и надежное хранение (Durability). Кэш же хранит временные копии данных (обычно в оперативной памяти) для ускорения доступа к ним.

Данные в кэше могут быть удалены в любой момент для освобождения места (политика вытеснения, например LRU), и приложение должно уметь прозрачно восстановить их из БД. Использование кэша позволяет снизить нагрузку на основную БД и значительно уменьшить время ответа приложения, но требует аккуратного управления инвалидацией данных при их изменении.

### Java integration

##### JDBC
JDBC (Java Database Connectivity) — это стандартный API для взаимодействия Java-приложений с базами данных. Он предоставляет набор интерфейсов, через которые можно выполнять SQL-запросы, получать результаты и управлять транзакциями, независимо от конкретной СУБД.

Хотя JDBC считается низкоуровневым и требует написания большого количества шаблонного кода (открытие соединений, обработка исключений, ручной маппинг ResultSet), он обеспечивает максимальный контроль над выполнением запросов и производительностью. Современные фреймворки, такие как Hibernate или Spring Data JPA, внутри себя используют именно JDBC.

##### connection pool
Connection pool (пул соединений) — это кэш готовых к использованию соединений с базой данных, который поддерживается специальным менеджером. Вместо того чтобы создавать новое физическое соединение для каждого запроса пользователя и закрывать его после, приложение "берет в аренду" свободное соединение из пула.

Самые популярные реализации для Java — HikariCP, Tomcat JDBC Pool и Druid. Использование пула является обязательным для любых серьезных приложений, так как создание нового соединения с БД — это очень дорогая операция, включающая сетевое рукопожатие, аутентификацию и выделение ресурсов на стороне сервера.

##### зачем нужен pool
Основная цель пула соединений — радикальное повышение производительности и масштабируемости приложения. Создание соединения с БД может занимать десятки и сотни миллисекунд, что недопустимо при обработке тысяч запросов в секунду. Пул позволяет сократить это время до микросекунд, возвращая уже открытое соединение.

Кроме того, пул ограничивает максимальное количество одновременных подключений к БД, предотвращая её перегрузку. Если все соединения заняты, новые запросы будут ждать в очереди, а не пытаться открыть новые сессии, что могло бы привести к отказу СУБД из-за исчерпания памяти или лимитов процессов.

##### transaction manager
Менеджер транзакций — это компонент, который координирует управление транзакциями в приложении. Он следит за тем, чтобы все операции в рамках одной логической единицы работы использовали одно и то же соединение и завершились либо успешно (COMMIT), либо отменой всех изменений (ROLLBACK).

В мире Spring это чаще всего `PlatformTransactionManager`. Он абстрагирует специфику различных технологий (JDBC, JPA, Hibernate) и позволяет использовать декларативное управление транзакциями через аннотацию `@Transactional`. Это гарантирует консистентность данных даже при выполнении операций в разных сервисах или репозиториях.

##### ORM vs raw SQL
Выбор между ORM (Object-Relational Mapping) и чистым SQL — это баланс между скоростью разработки и контролем. ORM (например, Hibernate) позволяет работать с данными как с Java-объектами, автоматически генерируя SQL и избавляя от рутины. Это ускоряет написание кода и упрощает его поддержку.

Чистый SQL (через JDBC или JDBCTemplate) незаменим для сверхсложных и высокооптимизированных запросов, где ORM может генерировать неэффективный код. SQL дает полный доступ к специфичным фишкам конкретной БД. Часто лучшим решением является гибридный подход: использование ORM для простых CRUD операций и чистого SQL для критичных по скорости отчетов.

### ORM

##### Hibernate
Hibernate — это самая популярная реализация спецификации JPA (Java Persistence API). Это мощный фреймворк, который берет на себя все задачи по маппингу Java-классов на таблицы БД, генерации SQL-запросов, управлению жизненным циклом объектов и кэшированию.

Он значительно упрощает работу с базами данных, позволяя разработчику сосредоточиться на бизнес-логике, а не на тонкостях JDBC. Однако Hibernate обладает высоким порогом вхождения: неправильное использование его механизмов (например, ленивой загрузки) может привести к серьезным проблемам с производительностью, таким как N+1.

##### Java Persistence API
JPA (Java Persistence API) — это стандартная спецификация Java EE и Jakarta EE, описывающая объектно-реляционное отображение. Она определяет набор интерфейсов и аннотаций (таких как `@Entity`, `@Table`, `@Id`), которые должны реализовать ORM-фреймворки.

Сам по себе JPA не является инструментом — это только "правила игры". Использование JPA вместо специфичных функций Hibernate делает код более переносимым: теоретически вы можете заменить Hibernate на EclipseLink или OpenJPA без переписывания всего кода маппинга.

##### persistence context
Контекст постоянства (Persistence Context) — это своего рода "первоуровневый кэш" и рабочая область для всех объектов сущностей, загруженных в рамках одной сессии или транзакции. Он гарантирует, что в рамках одной сессии одна строка из БД будет представлена ровно одним Java-объектом.

Все изменения, вносимые в объекты внутри контекста, отслеживаются (Dirty Checking). При завершении транзакции Hibernate автоматически синхронизирует эти изменения с базой данных, выполняя необходимые `UPDATE`. Это позволяет писать код в объектном стиле, не вызывая явно методы `save` для каждого изменения поля.

##### first-level cache
Кэш первого уровня — это неотъемлемая часть `EntityManager` (или `Session` в Hibernate). Он включен всегда и работает в рамках одной транзакции. Его задача — предотвращать повторные запросы к БД за одними и теми же данными в течение одного бизнес-процесса.

Если вы вызываете `find(User.class, 1)` дважды в одной транзакции, Hibernate выполнит SQL-запрос только в первый раз. Второй раз он просто вернет объект из памяти. Это не только ускоряет работу, но и обеспечивает консистентность: вы всегда работаете с одним и тем же экземпляром объекта.

##### entity lifecycle
Жизненный цикл сущности в JPA описывает состояния, в которых может находиться объект относительно контекста постоянства: **Transient** (новый объект, не связан с БД), **Managed** (объект в контексте, изменения отслеживаются), **Detached** (объект был в контексте, но сессия закрыта) и **Removed** (помечен на удаление).

Понимание этих состояний критично. Например, изменения в `Managed` объекте сохранятся сами, а для `Detached` объекта нужно вызвать `merge`, чтобы вернуть его в контекст. Ошибки при работе с состояниями часто приводят к тому, что данные не сохраняются в базу или возникают исключения при попытке сохранить уже удаленный объект.

##### lazy/eager
Это стратегии загрузки связанных данных. **Lazy** (ленивая) загрузка подгружает данные из БД только в момент первого обращения к ним в коде (используя прокси-объекты). **Eager** (жадная) загрузка вытягивает все связанные сущности сразу вместе с основным объектом (обычно через JOIN).

По умолчанию в JPA многие связи (например, `@OneToMany`) являются ленивыми для экономии ресурсов. Однако ленивая загрузка может привести к `LazyInitializationException`, если вы пытаетесь получить данные после закрытия транзакции. Выбор стратегии зависит от того, как часто вам действительно нужны связанные данные.

##### fetch join
`FETCH JOIN` — это специальная конструкция в языке запросов JPQL или HQL, которая позволяет переопределить ленивую стратегию загрузки для конкретного запроса. Она заставляет Hibernate выполнить SQL `JOIN` и сразу инициализировать связанную коллекцию или объект.

Это главный инструмент для борьбы с проблемой N+1. Вместо того чтобы сначала получить список родителей, а потом в цикле делать N запросов за детьми, `FETCH JOIN` позволяет получить все данные одним эффективным SQL-запросом. Это делает работу приложения предсказуемой и быстрой.

##### cascade types
Каскадные типы (Cascade Types) определяют, как операции над родительской сущностью должны распространяться на связанные с ней дочерние объекты. Например, `CascadeType.PERSIST` автоматически сохранит новых детей при сохранении родителя, а `CascadeType.REMOVE` удалит всех детей, если удален родитель.

Использование каскадов избавляет от необходимости вручную вызывать методы сохранения для каждого вложенного объекта. Самый мощный — `CascadeType.ALL`, включающий в себя все виды операций. Однако с каскадным удалением нужно быть очень осторожным, чтобы случайно не очистить половину базы данных при удалении одного пользователя.
